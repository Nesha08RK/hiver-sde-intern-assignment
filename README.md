# AI Customer Support Agent for AmazonHelp

## 1. Problem

This project builds a small, reproducible support-agent prototype for AmazonHelp conversations from the Customer Support on Twitter dataset. It classifies customer messages, retrieves similar historical support exchanges, drafts a grounded reply, and decides whether the case should be escalated.

## 2. Solution

The system uses a fixed nine-class taxonomy, a transparent keyword baseline, a TF-IDF plus logistic-regression baseline, TF-IDF historical retrieval, optional OpenAI-compatible response generation, deterministic fallback behavior, and an explicit escalation policy. The demo does not require an API key.

## 3. Architecture

```text
customer message
      |
      v
intent classifier ---> confidence ---> escalation policy
      |
      v
TF-IDF historical retrieval ---> evidence
      |
      v
deterministic grounded response generator
      |
      v
structured CLI output
```

## 4. Dataset

The raw TWCS dataset is expected at `data/raw/twcs/twcs.csv`. AmazonHelp has 2,811,774 rows in the local copy. Conversation roots are reconstructed using `in_response_to_tweet_id`, and roots with direct AmazonHelp replies are selected.

The golden set contains 200 deterministic AmazonHelp conversation roots selected with seed 42. Its labels are automatically generated weak labels and are explicitly marked `needs_manual_review`; they are not human annotations.

## 5. Intent taxonomy

1. Delivery and order fulfillment
2. Customer service escalation and feedback
3. Product condition, item accuracy, and seller issues
4. Digital products, devices, and apps
5. Prime membership and benefits
6. Returns, refunds, and charges
7. Pricing, offers, and product availability
8. Account access and security
9. Other/Unclear/non-substantive

Definitions, inclusion/exclusion rules, reviewed discovery frequencies, and examples are in `DECISIONS.md`.

## 6. Agent workflow

`SupportAgent` classifies the message, retrieves three similar customer-to-AmazonHelp examples from non-evaluation roots, generates a concise fallback response, and applies escalation rules for security, legal, payment, low-confidence, and unclear cases.

## 8. Baselines and evaluation

```powershell
python scripts\evaluate.py
```

`evaluate.py` evaluates the two intent baselines against the 200-row `golden_set.csv`, whose `intent` labels are weak rule-generated labels. It does not measure human performance:

| Model | Accuracy | Macro F1 |
|---|---:|---:|
| Keyword rules | 1.0000 | 1.0000 |
| TF-IDF + logistic regression | 0.7050 | 0.5034 |

The rule score is misleading: the evaluation labels were generated by the same rules. These numbers are a pipeline smoke test, not evidence of human-level performance. Results are written to `evaluation/results/`.

### What is misleading about my headline number?

The keyword-rule accuracy of `1.0000` is misleading because the evaluation labels were generated by the same keyword rules. It is label-reproduction accuracy, not independent model accuracy or human agreement. The TF-IDF result in the table is also against weak labels and should not be compared with the human-vs-model results as if they used the same reference labels.

## 9. Human-reviewed training and evaluation

`evaluation/human_training_set.csv` is a separate, balanced 90-example training file. Its `reviewer_intent` labels are manually reviewed and are used by `SupportAgent.from_project_files()` only after all 90 labels are complete. Conversation context is included in the classifier input. The original `RuleClassifier` remains available as a baseline.

`evaluation/golden_set_150.csv` is strictly evaluation-only. Run the human-vs-model agreement evaluation with:

```powershell
python scripts/human_agreement.py
```

The latest real results on 150 human-labelled examples are:

| Metric | Result |
|---|---:|
| Intent Cohen's kappa | 0.0624 |
| Intent percentage agreement | 18.67% |
| Escalation Cohen's kappa | 0.0000 |
| Escalation percentage agreement | 55.33% |

These are human-vs-model agreement results, not weak-label baseline metrics.

## Human-Evaluation Failure Modes

The following failure modes were identified from the 150-example human-labelled golden set:

1. **Digital products predicted as pricing — 10 cases.** Representative example `amz-0016` is a cashback eligibility question. Human: `Digital products, devices, and apps`. Model: `Pricing, offers, and product availability`. Hypothesis: sparse text features and overlapping commercial vocabulary cause the model to associate cashback/offer language with pricing even when the underlying issue is a digital product.
2. **Returns/refunds predicted as pricing — 8 cases.** Representative example `amz-0003`: “Need a revert urgently”. Human: `Returns, refunds, and charges`. Model: `Pricing, offers, and product availability`. Hypothesis: short, ambiguous wording provides too little lexical evidence and is mapped toward a better-represented class.
3. **Prime predicted as product condition — 6 cases.** Representative example `amz-0001` is an Amazon Music album download issue in a Prime-related conversation. Human: `Prime membership and benefits`. Model: `Product condition, item accuracy, and seller issues`. Hypothesis: the model overweights product-specific vocabulary and misses the broader Prime context.
4. **Pricing predicted as product condition — 6 cases.** Representative example `amz-0037`. Human: `Pricing, offers, and product availability`. Model: `Product condition, item accuracy, and seller issues`. Hypothesis: delivery/order vocabulary and sparse context can dominate the intended pricing signal.
5. **Returns/refunds predicted as product condition — 5 cases.** Representative example `amz-0011` is a Spanish complaint after one month. Human: `Returns, refunds, and charges`. Model: `Product condition, item accuracy, and seller issues`. Hypothesis: multilingual text and limited training coverage make the classifier rely on product-condition cues rather than the actual refund/return intent.

There were 122/150 intent mismatches and 67/150 escalation mismatches. Escalation mismatches were predominantly false escalations.

## 10. LLM judge

`python scripts\llm_judge.py` writes an unavailable status when `OPENAI_API_KEY` is absent. No fake judge scores are produced. `.env.example` documents the optional variable.

## 11. Failure analysis

`evaluation/results/failure_analysis.json` contains actual mismatches from the latest run. The most important current limitation is weak-label evaluation: rule-generated labels reward the rule baseline and do not measure real human agreement. Other observed errors are overlapping delivery/Prime/payment language, sparse minority classes, multilingual text, and context-dependent follow-ups.

## 12. Limitations and next-week improvements

The prototype does not claim production accuracy, does not call an LLM by default, and does not infer unavailable order data. Manual annotation should replace weak labels before model selection. Next steps are reviewing the golden set, adding more labeled examples for minority intents, improving multilingual normalization, and configuring a tested LLM adapter if required.

## Manual Annotation UI

The local annotation UI reviews one example at a time and saves only reviewer fields. For the evaluation set, it saves `reviewer_intent`, `reviewer_expected_escalation`, and `reviewer_notes` in `evaluation/golden_set_150.csv`. It does not generate labels. The escalation selector saves Yes as `ESCALATE` and No as `AUTO_HANDLE`.

Start it from the repository root:

```powershell
venv\Scripts\python.exe scripts\annotate_golden_set.py
```

Open http://127.0.0.1:8765/ in a browser. Use `Save and Next` to persist a completed example. Saved annotations are loaded from the CSV when the UI restarts, and the current position is remembered in the browser. To use another port:

```powershell
venv\Scripts\python.exe scripts\annotate_golden_set.py --port 8766
```

To annotate the separate 90-example human-training set, use:

```powershell
venv\Scripts\python.exe scripts\annotate_golden_set.py --csv evaluation\human_training_set.csv
```

This mode saves only `reviewer_intent` and `reviewer_notes`. The completed file is used for model training and remains separate from the 150-example evaluation set.
